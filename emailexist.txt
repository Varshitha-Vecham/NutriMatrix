# Feature: Email Existence Verification Before OTP Registration

## Project Context

I am developing NutriMatrix, an AI-powered nutrition and smart grocery platform.

My project uses:
- Frontend: React, HTML5, CSS3, JavaScript
- Backend: Node.js and Express
- Database: MySQL
- Email service: Gmail SMTP using Nodemailer
- Authentication: Email OTP verification
- Environment configuration: `.env`

Inspect the existing project files before making any changes. Identify the current registration endpoint, OTP generation and verification logic, email-sending function, and frontend registration component.

IMPORTANT: Preserve all existing functionality, UI design, CSS, login functionality, password validation, MySQL configuration, and OTP expiry/resend functionality.

## 1. Main Requirement

I want to verify whether an entered email address is deliverable BEFORE generating or sending an OTP.

Currently, the registration form may accept an email address that has a valid format but does not correspond to an existing mailbox.

For example:
`v2134_@gmail.com`

Even if the address passes format validation, the system should not automatically assume that the mailbox exists.

I want an email verification API, such as ZeroBounce, to check the address before the existing OTP process begins.

Do not rely only on regular expressions or email format validation.

## 2. Required Registration Flow

Implement the following sequence:

Step 1: The user opens the NutriMatrix registration page.

Step 2: The user enters their name, email address, and other required registration details.

Step 3: When the user clicks the existing registration button, the frontend sends the required information to the backend.

Step 4: Before generating an OTP or sending an email, the backend checks whether the email is already registered in the MySQL database.

If the email is already registered, display an appropriate message and do not send an OTP for a new registration.

Step 5: If the email is not already registered, the backend calls the configured email verification API.

Step 6: Interpret the API result according to the provider's official documentation.

If the API confirms that the email is invalid or the mailbox does not exist, display:

"Invalid email address. Please enter an existing email."

Do not generate an OTP, send an OTP email, or create a registered user account.

Step 7: If the API returns a valid/deliverable result, continue with the existing OTP registration process.

Step 8: Send the OTP using the existing Gmail SMTP configuration.

Step 9: Keep the current OTP verification process and complete account registration only after successful OTP verification.

IMPORTANT: A verification API's "valid" result does not guarantee that a mailbox exists. Use the provider's documented result categories accurately.

## 3. Email Verification API Integration

Use ZeroBounce Email Validation API as the initial integration option.

Official documentation:
https://www.zerobounce.net/docs/email-validation-api-quickstart/v2-validate-emails

Before implementing the integration:

1. Check the official API documentation for the correct endpoint, authentication method, request parameters, and response format.
2. Use the currently supported API version.
3. Identify the API result fields that distinguish valid, invalid, catch-all, unknown, and other applicable statuses.
4. Do not invent API response fields or assume that every provider returns the same status values.
5. If ZeroBounce is unavailable or its free allowance is exhausted, handle the error gracefully.

Keep the implementation compatible with the existing Node.js/Express backend.

Use Node.js's built-in fetch if supported by the current Node.js version. Do not install unnecessary packages.

If an SDK is genuinely required, explain why before adding it.

## 4. Environment Variables and API Key Security

Store the API key in the backend `.env` file:

ZEROBOUNCE_API_KEY=your_actual_api_key

Use the appropriate environment variable name consistently throughout the code.

Requirements:
- Never hardcode the API key in source code.
- Never expose the API key through React or Vite environment variables.
- Never return the API key in an API response.
- Do not commit `.env` to Git.
- Ensure the backend loads environment variables using the project's existing configuration.
- If the API key is missing, return a clear server-side configuration error without sending an OTP.
- Never silently skip email verification when the API fails.

Do not print the full API key in terminal logs.

## 5. API Result Handling

Handle verification results carefully.

A. Confirmed invalid email:
- Reject the registration attempt.
- Do not send an OTP.
- Display: "Invalid email address. Please enter an existing email."

B. Valid/deliverable email:
- Continue to the existing OTP process.

C. Unknown or inconclusive result:
- Do not automatically classify the email as nonexistent.
- Do not send an OTP if the application's configured policy requires successful verification before OTP delivery.
- Display: "We couldn't verify this email address. Please try again."

D. Catch-all or risky result:
- Follow the provider's documented meaning.
- Do not claim the mailbox definitely exists or definitely does not exist.
- Apply an explicit policy rather than treating every non-invalid result as valid.

E. API timeout, network error, rate limit, or service failure:
- Do not generate or send an OTP.
- Display a suitable retry message.
- Log a safe diagnostic message on the backend.
- Never expose sensitive API response details to the user.

F. Missing API key:
- Do not bypass verification and continue registration.
- Return an appropriate server error and explain the missing configuration in server logs.

## 6. Prevent Duplicate API Calls

Avoid calling the email verification service repeatedly for the same registration submission.

Requirements:
- Disable the registration button while the verification request is processing.
- Prevent duplicate requests caused by repeated clicks.
- Add reasonable request timeouts.
- Handle concurrent registration requests safely.
- Recheck whether the email is already registered before creating the account.
- Do not introduce permanent caching that could incorrectly reuse stale verification results.

Respect the API provider's usage limits and avoid unnecessary requests.

"Invalid email address. Please enter an existing email."

Inconclusive verification:
"We couldn't verify this email address. Please try again."

Verification service unavailable:

Do not display success messages before the backend confirms the corresponding operation succeeded.
